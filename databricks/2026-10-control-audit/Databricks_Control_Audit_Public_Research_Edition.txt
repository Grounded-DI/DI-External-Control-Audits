CHAPTER 01 UNITY GATEWAY


Following an argument to the boundary
Unity Gateway’s relayed Claude launch is intended to exclude general user settings while supplying its own
registrations. The source explains a practical reason: a stale user-scope apiKeyHelper should not shadow
subscription OAuth. The builder adds --setting-sources project,local before caller arguments. The question
was whether a caller could supply a conflicting --setting-sources user and change the downstream selection.
An argument list is an instruction to another program. Two conflicting options show what the sender passed;
they do not show what the receiver ultimately loaded. A parser might choose the first, choose the last,
combine them, or reject them. The investigation reached several sender-side boundaries without obtaining
the native receiver’s answer.

The evidence grew in stages
The oldest retained audit could not collect tests with pytest or import the full module because dependencies
were missing. It extracted three unchanged function bodies with Python’s syntax tree tools and supplied
stubs. Eight assertions passed per process, but this did not demonstrate an integrated launch or real
persisted state. The failed setup receipts remain in the record.
The continuation obtained compatible dependencies, though not the exact upstream lockfile, and imported
the real managed_config module. A selected upstream suite recorded 174 passes. Eight frozen real-module
cases passed in each of two processes, including refusal of a workspace mismatch before cache or token

CHAPTER 02 CURSOR MCP


Preserving a damaged configuration
Cursor’s MCP registrations live in a shared JSON document. The pinned writer promises to merge entries
while preserving unrelated content. The audit asked a recovery question: what happens if that document is
already malformed? It redirected the real writer to a disposable file containing the synthetic bytes shown
below. No actual Cursor application, complete configure command or MCP service was exercised.

EXHIBIT 04 THE MALFORMED INPUT
  before = b'{"mcpServers":'
  operation = write_mcp_server_config("svc", ["ug", "proxy"])
  observed = new JSON containing svc replaced the original bytes
  return value = False
Synthetic input and return value from a retained local probe; direct and batched registration showed the stated transition.


The mechanism is direct. read_json_safe converts malformed input into an empty object. The writer adds its
new registration to that object, and write_json_file writes the resulting JSON. The old bytes no longer remain
in that file. A person might have repaired some damaged contents manually, so overwriting can matter even
when parsing failed.
The limit is equally important. The source deliberately treats malformed JSON as empty, and its general
preservation language does not explicitly promise damaged-file recovery. The evidence supports a local
preservation concern and a proposed preserve-and-deny policy. It does not establish a customer incident,
unauthorized access, a hosted authorization bypass, or a definite violation of a malformed-input contract.

The return value is not an authorization decision
The direct writer’s False means that the parsed map did not already contain the named server. It does not
mean a permission check failed. The batch path likewise works with registrations and removals, not a
demonstrated general identity boundary. The tests do not establish caller authorization, ownership policy
outside the tested helper, filesystem permission behavior or concurrent-write behavior.

   The original seven custom tests passed because they asserted the recorded observations and
   controls. Later sidecars made preservation the expected property and therefore went red on the
   original. Those results are consistent once the expectation is stated.

CHAPTER 03 SQL RETRY


When two seconds becomes thirty
Retry-After tells a client how long to wait before trying again. The selected SQL connector method says it
sleeps for that header duration, yet applies max(proposed_wait, delay_max). With delay_max set to thirty,
the expression acts as a floor. A two-second header therefore became a thirty-second requested wait in the
recorded local probe.
The audit copied the pinned retry and exception files into a minimal package shim. A synthetic response
supplied the header; time and sleep were mocked. The clock and start time were fixed at 100. There was no
actual delay, HTTP request, credential or database action. The exhibit records requested sleeps, not elapsed
wall-clock measurements.
EXHIBIT 05 RECORDED RETRY OBSERVATIONS

 Header                 Total budget                  Requested sleep                      Result

 2 seconds              900 seconds                   30 seconds                           Returned True

 30 seconds             900 seconds                   30 seconds                           Control passed

 60 seconds             900 seconds                   60 seconds                           Returned True

 2 seconds              10 seconds                    None                                 MaxRetryDurationError


The budget case explains the practical concern. A two-second header would fit inside ten seconds, but the
proposed thirty-second wait is rejected before sleep. This establishes a local retry-availability discrepancy
under the selected inputs. It does not establish an outage or how a real server and connector transport would
behave.
The sixty-second row needs a different interpretation. A server’s longer delay may be a minimum the client
should respect. Exceeding a parameter called a maximum is not enough, by itself, to prove that honoring the
server is wrong. The stronger finding is the inflation of a small positive header. A second probe through
inherited urllib3 Retry.sleep confirmed dispatch to this override under the same mocks, not a full request
path.

Status decisions supplied counterevidence
Direct method controls declined a synthetic POST ExecuteStatement 500 without an override, accepted 429,
accepted forced 500 under the documented override, and in server-directed mode required a header for 429.
These controls prevent a timing discrepancy from becoming a blanket claim that retry safety failed.

CHAPTER 04 BOOLEAN CONVERSION


A clear output and an unclear invalid input
policy
The SEA result converter maps recognized true strings to True and other strings to False. The audit asked
what happens to values outside the familiar true/false pair. It called the converter directly with synthetic
inputs, without a service response or database.

EXHIBIT 08 RECORDED CONVERSION OUTPUTS
  boolean "true"     -> True
  boolean "false"    -> False
  boolean "unknown" -> False
  boolean "TRUE "    -> False
  int "not_a_number" -> "not_a_number"                (str)
Recorded synthetic converter outputs; the invalid-integer branch logged a warning. Repeated and clean results matched.


The implementation lowercases the string and checks membership in a true-value list. It does not strip
whitespace. Thus TRUE followed by a space is a whitespace case, not evidence that ordinary uppercase
TRUE fails. An unknown string is outside the list and becomes False without raising an exception.
The invalid integer control followed a different path: conversion raised an exception, which the general
handler logged before returning the original string. That contrast shows how the code behaves. It does not
create an implicit promise that every invalid boolean must also raise or preserve the original input.

   Disposition: PARTIAL. The mapping is demonstrated, but the record identifies neither a required
   invalid-boolean policy nor evidence that the SEA service supplies these malformed values.

What held and what would settle it
All six upstream conversion tests passed, including valid true and false spellings. Multiple assertions inside
the boolean test are not additional pytest tests. No candidate change was proposed, because choosing
rejection, preservation or coercion would first require an input contract and caller context.
The next evidence would be a versioned description of allowed service values and validation at the caller

SYNTHESIS


What changed in Grounded DI’s method
The exercise made the distinction between observation and judgment concrete. A decimal cast unable to
represent its input has a stated representation contract. A changed manifest has a copy promise. An
unknown boolean coerced to false needs an invalid-input policy before it can be called a violation. A
damaged Cursor file invites a stronger recovery safeguard, but the safeguard must not be attributed to
upstream code as an existing authorization contract.

Write the property before scoring the result
Registered sidecars made the expected behavior explicit and preserved case membership between original
and candidate. That strengthened comparison, but it did not settle whether every property was the right
specification. The Fallen Warriors method’s warning about replay and semantic correctness applies to the
auditor’s own assertions as much as to the target.

Use passing controls to constrain a repair
Retry v1 is the clearest example. It improved the new cases while breaking the no-header behavior that
upstream tests expected. Keeping that failed attempt made the refined repair explainable. The same
discipline preserved ordinary decimal values, correct filtered rows, valid Cursor entries and host-keyed
tokens alongside failures.

Treat the harness as another tested implementation
The lean schema failure was in Grounded DI’s packaging, not Databricks. The cache recheck then showed
why integrity and test success answer different questions. The candidate packaging did not become
trustworthy merely because its bytes were hashed: the verifier needed a compatible schema, and the
extraction needed to remain unchanged after its child processes ran.

Preserve corrections as evidence
The existing retry report changed the novelty claim. The blank endpoint capture required a new capture. A
malformed fixture needed a corrected stub. A virtual-environment path needed a portability correction.
Retaining those stages lets a skeptical reader see why confidence increased or a claim narrowed, rather than
receiving only a polished final green line.

   The practical output is a more disciplined record: explicit properties, bounded conclusions, separate
   candidates, stable identifiers, preserved failures and a replay path that states its missing inputs.
   None of that requires a product-wide verdict or an invented certification.
